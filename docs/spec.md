## 목표
`pip freeze`로 만든 requirements.txt와 OS·Python 버전을 알려주면, 지원 종료일·취약점·
**지금 Python에서 설치 가능한 안전한 버전**을 조회해서 회차별 패치 계획을 만들고, 저장·수정·삭제할 수 있는 Agent 서비스.

## 사용자와 하는 일 (일상어)
1. 대화 탭에서 `pip freeze > requirements.txt`로 만든 파일을 올리고, "Ubuntu 20.04, Python 3.8"이라고 적는다.
2. "이번에 5개까지, 첫 점검은 11/21 22~24시, 격주로"라고 말한다.
3. Agent가 단계(분석 → 계획 → 조회 → 판단 → 재계획 → 응답)를 보여주며 회차별 계획을 제안한다.
   - 예: "django를 고치려면 Python 3.10이 필요해서, 1회차에 Python 업그레이드를 먼저 넣었어요."
4. "확정해줘"라고 하면 회차 하나하나가 계획으로 저장된다.
5. 계획 관리 탭에서 날짜·시간·항목을 고치거나 지운다. 시간이 겹치면 경고가 뜬다(저장은 됨).
6. 실행 로그 탭에서 Agent가 무슨 Tool을 왜 불렀고, 왜 재계획했는지 본다.

## 확정한 결정
| 주제 | 결정 |
|---|---|
| 입력 | freeze로 만든 requirements.txt 업로드 + OS·Python 버전은 대화 문장 |
| 받는 OS (v1.17) | 리눅스 서버뿐 아니라 **백엔드를 돌리는 PC**도 받는다: Ubuntu 등 리눅스, macOS, Windows. 상세는 "OS 입력 (v1.17)" |
| 파일 처리 | `이름==버전` 줄만 조회. `-e`, `@ file://`, `>=` 등은 "조회 제외" 목록으로 보여주고 되묻지 않음 (상세: "requirements.txt 파싱 규칙") |
| 점검 용량 | 사용자가 "이번에 N개까지"라고 말함. 소요 시간은 다루지 않음 |
| 우선순위 | 취약점 심각도 높은 순 → 같으면 지원 종료가 빠른 순 |
| 핵심 제약 | 고칠 버전이 **현재 Python에서 설치 가능해야 함** (PyPI의 requires_python) |
| 재계획 | ① 호환 제약 위반 → 다른 버전 재조회 또는 Python 업그레이드를 계획에 추가 ② N 초과 → 다음 회차로 나눔. 상한 3회 |
| 빠진 입력 | Tool 부르기 전에 빠진 것만 되묻기 (기본값 쓰지 않음). 빠진 것 판단과 되묻는 문장은 코드가 만든다 (LLM은 spec 밖 정보까지 묻는 경향, 2026-11-18 확인). Tool에 필요한 것(파일·OS와 버전·Python)이 빠지면 되묻고 끝. 일정(N·첫 점검 날짜·간격)만 빠지면 **조회·판단은 해서 우선순위를 먼저 보여 주고** 회차로 나누는 데 필요한 일정만 되묻는다. 시각은 선택. **OS 이름은 알고 버전만 빠졌으면 그 OS의 버전만 묻는다** (v1.17, 아래 "OS 입력") |
| 저장 단위 | 점검 회차 1개 = 계획 1개 |
| 겹침 | 계획에 날짜 + 시작·종료 시각(선택). 시각이 없으면 하루 전체로 보고, 같은 날 시간이 겹치면 경고 |
| Ubuntu 지원 종료 | 일반 지원 종료일 기준. 확장 지원(ESM) 종료일은 참고로 함께 표시 |
| 지원 종료된 OS·Python | 심각도 HIGH와 같은 순위 |
| 심각도 | OSV `database_specific.severity` 글자 등급(CRITICAL / HIGH / MODERATE / LOW)을 그대로 씀 |
| 중복 취약점 | OSV는 같은 취약점을 GHSA·PYSEC 두 건으로 줄 수 있음 → `aliases`로 묶어 1건으로 세고, 등급은 있는 쪽 사용 |
| 심각도 미상 취약점 | 묶은 뒤에도 등급이 없으면 LOW 다음 "심각도 미상" 칸. 임의로 등급을 매기지 않음 |
| 회차 간격 | "매주 / 격주 / 매월" 또는 "N일" → 일 수로 바꿔 저장 |
| Memory | 조건(패키지 목록, OS·Python, N, 첫 점검 날짜·시각, 회차 간격) + 직전 사용자 메시지·직전 답·직전 제안 계획 (API 결과는 매번 다시 조회). 직전 대화는 analyze에 넘겨 후속 요청 해석에 쓰고, 조건은 바뀐 값만 덮어씀 (F3010). 직전 제안 계획은 "확정해줘"의 대상 |
| 화면 | 탭 3개: 대화 / 계획 관리 / 실행 로그 |
| 심화 | 필수 기능 끝난 뒤 정함 |

## Tool 명세 (모두 `{ok, data}` 또는 `{ok:false, error:{code, message}}`)
| Tool | 종류 | 언제 쓰나 (Agent에게 주는 설명) | 입력 | data | 실패 코드 |
|---|---|---|---|---|---|
| get_eol | external | OS나 Python이 언제까지 지원되는지 알아야 할 때 | product, cycle | eol_date, esm_date(없으면 null), is_eol, lts, latest_patch, label, link, queried_cycle, note | PRODUCT_NOT_FOUND, NO_EOL_DATE, UPSTREAM_ERROR, TIMEOUT |
| get_vulns | external | 특정 패키지 버전이 위험한지, 몇 버전에서 고쳐졌는지 알아야 할 때 | name, version | count, vulns[{id, severity, fixed_versions}], truncated | UPSTREAM_ERROR, TIMEOUT |
| get_package_versions | external | 업그레이드할 버전이 지금 Python에서 설치되는지 알아야 할 때 | name | latest, project_url, versions[{version, requires_python, yanked}] | PACKAGE_NOT_FOUND, UPSTREAM_ERROR, TIMEOUT |

요구사항 ↔ Tool:
| 요구사항 | Tool | 지키는 방법 |
|---|---|---|
| F3002 후보 확보 | get_vulns | 취약한 패키지 = 계획 후보. 다음 단계용 식별자로 취약점 id·수정 버전 반환. 페이지 상한(10쪽)을 넘겨 일부만 받으면 `truncated: true` |
| F3003 상세 속성 | get_package_versions | 판단 속성 requires_python. 비어 있으면 채우지 않고 null("호환 미확인"). 사용자용 링크 project_url |
| F3004 다른 출처 보조 정보 | get_eol | 사용자용 이름(label)·링크(link). 결과 없음 = PRODUCT_NOT_FOUND, 종료일 없음 = NO_EOL_DATE |
| F3002 기준 차이 밝히기 | get_eol | cycle에 패치 번호가 붙어 오면(3.8.10, 20.04.6) 줄기(3.8, 20.04)로 바꿔 조회하고 `queried_cycle`·`note`로 밝힘 |

처리 규칙:
- HTTP 상태 → 실패 코드: 404 → 그 Tool의 NOT_FOUND 코드(get_vulns는 404 없음), 429·5xx·그 밖의 비정상·JSON 아님·연결 실패 → UPSTREAM_ERROR, 시간 초과 → TIMEOUT.
- OSV는 모르는 패키지도 200 `{}`로 답한다 → 0건(성공). 패키지가 실제로 있는지는 get_package_versions가 판단.
- OSV 중복 묶기: id·aliases가 겹치면 1건, 등급은 있는 쪽. 수정 버전은 그 패키지(PyPI)의 ECOSYSTEM 범위 `fixed` 값만 모아 중복 없이 (GIT 범위의 fixed는 커밋 해시라 뺌).
- PyPI: 파일이 하나도 없는 버전은 설치할 수 없으므로 목록에서 뺀다. 파일이 모두 yanked인 버전만 `yanked: true`. requires_python은 파일들 중 처음 나오는 값.

- 종류: `external` = 외부 API를 감싼 Tool, `local` = 이 서버 안의 기능을 부르는 Tool(지금은 없음).
- 공통 실패 코드 (모든 Tool, 레지스트리가 붙임):
  | 코드 | 언제 |
  |---|---|
  | INVALID_INPUT | 입력이 빠졌거나 비었거나 형식이 틀림 |
  | UNKNOWN_TOOL | 등록되지 않은 Tool 이름 |
  | INTERNAL_ERROR | Tool 안에서 예상 못 한 예외 (밖으로 던지지 않고 이 코드로 바꿈) |
- 등록: Tool마다 입력은 pydantic 모델 하나로 정의한다. LLM에 넘기는 입력 형식과 입력 검사가 모두 이 모델에서 나온다.
- 취약점 0건은 실패가 아니라 `ok:true, count:0`.
- Tool 하나가 실패해도 그 항목만 "확인 못 함"으로 두고 나머지는 진행.
- 파일 파싱, 버전 비교 계산, 회차 나누기, 계획 저장은 Tool이 아니라 실행 흐름(코드)이 직접 한다.

## OS 입력 (v1.17)
리눅스 서버 대신 개인 PC를 백엔드 서버로 쓰는 경우도 받는다. 2026-11-19 endoflife.date 실제 응답으로 확인한 내용:

| OS | 사용자 말 예시 | 조회 (product / cycle) | 실제 응답 | 처리 |
|---|---|---|---|---|
| Ubuntu | "우분투 20", "Ubuntu 22.04" | `ubuntu` / `20.04` | 종료일 있음 | 지금 그대로 |
| macOS | "맥북", "macOS 15", "세쿼이아" | `macos` / 주 버전 숫자(`15`, `26`) | 지원 중이면 `eolFrom: null`, `isMaintained: true` → 지금은 `NO_EOL_DATE` 실패 | **실패가 아니라 "지원 중 (종료일 미발표)"** |
| Windows | "윈도우 11 24H2" | `windows` / `11-24h2-w` | `11`만으로는 `PRODUCT_NOT_FOUND` (실제 이름은 `11-25h2-w`·`11-25h2-e` 꼴) | 주 버전 + 기능 업데이트(24H2 등)로 cycle을 만든다 |

- **OS 이름만 있고 버전이 없으면** 그 OS에 맞는 버전만 묻는다. 같은 문장을 두 번 내지 않는다.
  - 2026-11-19 재현: "Python 3.11, 5개, 11/25 매주" → OS를 물음 → "로컬 맥북을 백엔드 서버로 써요" → os=macos, 버전 없음 → **똑같은 "OS와 버전 (예: Ubuntu 20.04)"을 또 물음**.
  - 고친 뒤: 두 번째 답은 "macOS 버전만 알려 주세요 (예: macOS 15 — 이 Mac에 관하여에서 확인)"처럼 받은 OS를 인정하고 빠진 것만 묻는다.
  - Windows는 주 버전만 있으면 기능 업데이트를 묻는다 (예: "Windows 11 24H2 — 설정 > 시스템 > 정보"). 에디션을 말하지 않으면 Home/Pro(`-w`)로 조회하고 응답에 그렇게 적는다.
  - "로컬 PC", "내 컴퓨터"처럼 OS 이름이 없으면 지금처럼 OS와 버전을 묻되, 예시에 macOS·Windows도 넣는다.
- 이름 정규화는 코드가 한다 (`normalize_os_version`처럼): 맥·맥북·macOS·OS X → `macos`, 윈도우·Windows → `windows`, 코드네임(세쿼이아 → 15, 타호 → 26)은 아는 것만 바꾸고 모르면 되묻는다. 지어내지 않는다.
- get_eol: `eolFrom`이 없고 `isMaintained: true`면 `ok:true`, `eol_date: null`, `is_eol: false`, `note: "지원 중 (종료일 미발표)"`. `isMaintained`도 false면 지금처럼 `NO_EOL_DATE`.
- 지원 중인 OS는 계획 항목이 아니다(지금 규칙 그대로). 종료일이 없으므로 우선순위 계산에서 "남은 일수"는 가장 긴 것으로 본다.
- 테스트: macOS·Windows 응답 저장본을 `tests/fixtures/`에 더하고(네트워크 없이), 위 재현 대화가 두 번째에 버전만 묻는지 확인한다.

## requirements.txt 파싱 규칙
Tool이 아니라 실행 흐름이 직접 한다 (`app/parsing/requirements.py`). 오류를 내지 않고 모든 줄을 "조회" 또는 "제외(이유)"로 나눈다.

| 줄 | 처리 |
|---|---|
| `django==2.2.0` | 조회 |
| `Django[argon2]==2.2.0` | 조회. 추가 기능 표시(`[...]`)는 뗌 |
| `django==2.2.0  # via x` | 조회. 줄 끝 주석은 뗌 |
| `pywin32==306 ; sys_platform == "win32"` | 조회. 환경 표시는 떼고 `marker`로 남김 ("환경 조건 있음") |
| 줄 끝 `\` 이어진 줄, `--hash=…` | 이어 붙여 한 줄로 보고 해시는 무시 |
| 빈 줄, `#` 주석 줄 | 무시 (제외 목록에도 안 넣음) |
| `-e …`, `pkg @ …`, `git+…` 등 URL·경로 | 제외: PyPI 출처 아님 |
| `>=`, `<`, `~=`, `!=`, `==1.*`, `===` | 제외: 정확한 버전 아님 |
| `-r`, `-c`, `--index-url` 등 옵션 줄 | 제외: 옵션 줄 |
| 버전 없는 `django` | 제외: 버전 없음 |
| 같은 패키지 두 번 (이름은 소문자·`-_.` 같게 봄) | 처음 줄만 조회, 나중 줄은 제외: 중복 |
| 해석할 수 없는 줄 | 제외: 형식 오류 |

- 결과: `packages[{name, version, line_no, marker}]`, `excluded[{line_no, text, reason}]`. 줄 번호는 이어진 줄의 첫 줄 기준.
- 인코딩: 앞머리 표시(BOM)를 보고 UTF-8 / UTF-16(Windows PowerShell의 `pip freeze >` 기본) 모두 읽는다. BOM이 없으면 UTF-8, 실패하면 latin-1.

## 판단 규칙
### 목표 버전 고르기 (패키지마다)
1. get_package_versions로 **현재 Python에서 설치 가능하고 yanked가 아닌 정식 버전 중 가장 최신**을 고른다.
   정식 버전이 아닌 것(rc·a·b·dev 시험판)은 후보에서 뺀다 (실측: django 56개).
   requires_python이 비어 있는 버전은 후보로 두되 "호환 미확인"으로 표시한다.
2. 그 버전을 get_vulns로 다시 조회해 취약점 0건인지 확인한다.
3. 0건이면 목표 버전 확정. 주 버전이 바뀌면(예: 2.x → 4.x) "큰 변경" 표시.
4. 0건이 아니면 **호환 제약 위반**: 지금 Python으로는 안전한 버전에 갈 수 없다는 뜻 → 재계획.
5. 지금 Python에 설치 가능한 버전이 아예 없거나, 고른 버전이 **현재 버전보다 높지 않으면**(다운그레이드)도 위반으로 보고 재계획한다.

> 왜 바꿨나: 실측에서 django 2.2.0의 수정 버전이 `2.2.28 / 3.2.13 / 4.0.4`처럼 줄기별로 여러 개 나왔고,
> 낮은 수정 버전은 그 뒤에 나온 취약점을 또 갖고 있어요. "가장 낮은 수정 버전부터 시도"하면 시도 횟수만 쓰고 실패해요.
> "호환되는 최신 버전 하나를 확인"하면 패키지당 추가 호출이 1번이고, 실제 운영 관행과도 맞아요.

### 재계획
| 상황 | 하는 일 | 다시 부르는 Tool |
|---|---|---|
| 호환 제약 위반 패키지가 있음 | 아래 "필요한 가장 낮은 Python 구하기"로 Python 목표를 정하고, 지원 중이면 "Python 업그레이드"를 앞 회차에 넣고 해당 패키지를 그 뒤 회차로 | get_vulns(줄기별 후보 버전), get_eol(python, 새 줄기) |
| 새 Python이 지원 종료됨 | 그 다음 줄기로 한 번 더 시도 (위반 패키지의 목표 버전도 그 줄기 기준으로 다시 확인). 상한까지 안 되면 "보류(사유)"로 표시 | get_eol, get_vulns |
| 우선 항목 수 > N | 넘친 항목을 다음 회차로 | 없음 |
| 회차 날짜가 그 항목의 지원 종료일 뒤 | "종료 이후 처리" 경고 | 없음 |

**필요한 가장 낮은 Python 구하기**
1. 현재 Python의 다음 줄기(3.8이면 3.9, 2.x면 3.0)부터 하나씩 올린다. 어디까지 올릴지는 requires_python 조건에 나오는 가장 높은 줄기 + 1 (연산자 무관: `>3.9`, `~=3.10`, `==3.11.*` 모두).
2. **패키지마다 따로** "그 줄기에서 설치 가능한 최신 정식 버전"을 고른다 (get_package_versions 결과 재사용, 추가 호출 없음).
   그 버전이 앞 줄기와 다를 때만 get_vulns로 확인한다. 0건이 처음 나오는 줄기가 그 패키지의 최소 줄기.
3. 패키지별 최소 줄기 중 **가장 높은 것**이 Python 후보다.
   - 취약점 조회가 실패해 판단 못 한 패키지는 "확인 못 함" 목록으로 빼고, 나머지 패키지는 계속 진행한다.
   - 어떤 줄기에서도 0건 버전이 없는 패키지는 "보류(어떤 Python 줄기에서도 취약점 없는 버전이 없음)".
4. get_eol(python, 후보)로 지원 중인지 확인한다. 종료됐으면 다음 줄기로 (위 표 2행).

- 상한: 재계획 3회, 회차 최대 3개. 넘친 것은 "미배정" 목록.
- 재계획 1회 = **Python 후보 줄기 하나를 정해 get_eol로 확인하는 것.** 1번의 줄기 훑기(get_vulns)는 세지 않는다.
  (예시: 3.10 시도 → 종료 → 3.11 시도 → 지원 중 = 2회)
- 재계획 안 함: 입력 부족, 모든 Tool이 같은 이유로 실패(네트워크 등) → 바로 안내 (판단 단계로 가지 않음).
- 재계획 방식(LLM 선택): 기본은 Python 업그레이드. 사용자가 Python 업그레이드를 명시적으로 거부했을 때만 "보류".
- 순서 제약: Python 업그레이드 항목은 그걸 필요로 하는 패키지보다 항상 앞 회차.
- 같은 일은 한 항목: 현재 Python이 지원 종료라 생긴 항목과 재계획으로 생긴 Python 업그레이드 항목은 **"Python 3.8 → 3.11" 한 항목**으로 합친다. 등급은 둘 중 높은 쪽.

### 회차 나누기
1. 항목을 우선순위대로 줄 세운다.
2. **순서 제약이 우선순위보다 먼저다**: 앞 회차에 있어야 할 항목(Python 업그레이드)이 들어가기 전에는, 그걸 필요로 하는 항목을 같은 회차나 앞 회차에 넣지 않는다.
3. 회차마다 N개까지 채운다. Python 업그레이드·OS 항목도 N개 중 하나로 센다.
   (예시: django가 CRITICAL이어도 Python 업그레이드에 묶여 2회차)

### 우선순위
CRITICAL > HIGH(지원 종료된 OS·Python 포함) > MODERATE > LOW > 심각도 미상 (패키지의 등급 = 가진 취약점 중 가장 높은 등급) → 같으면 지원 종료까지 남은 일수가 적은 순. 취약점 0건 항목은 계획에 넣지 않고 "안전" 목록으로.
- Tool 실패로 취약점·버전을 확인 못 한 패키지는 회차에 넣지 않고 **"확인 못 함" 목록**으로 따로 보여준다 (등급을 모르므로 순서를 정할 근거가 없음).
- 지원 중인 OS·Python은 항목이 아니다 (재계획으로 Python 업그레이드가 필요할 때만 Python 항목이 생김).
- Python 업그레이드 항목의 등급은 HIGH로 둔다 (지원 종료면 원래 HIGH, 지원 중이어도 다른 항목의 전제 조건이라 HIGH).
- Python 버전은 줄기("3.8")로 받으므로 3.8.0으로 보고 requires_python을 판정한다. `>=3.8.1`처럼 패치 단위 조건은 제외될 수 있다 (드묾).

## LLM이 하는 일 / 코드가 하는 일
| LLM | 코드 |
|---|---|
| 의도 분류(계획 수립 / 사실 조회 / 계획 확정 / 그 밖의 대화)와 이유 | 파일 파싱 |

## 구현 방식
- 백엔드: FastAPI + SQLite. Agent: LangGraph 상태 그래프, LLM은 OpenAI(langchain-openai). 화면: HTML/CSS/JS.
- 버전 비교·requires_python 판정은 `packaging` 라이브러리 사용 (수업 필수 목록 밖, 추가 결정: docs/decisions/2026-11-18-packaging.md)
- 로깅 Agent 분리: 메인 Agent는 이벤트를 큐에 넣기만 하고, 로깅 Agent가 따로 꺼내 저장. 로깅이 죽어도 메인은 기다리지 않음.
- 요청 하나 안에서 같은 API 호출 결과는 캐시해서 재사용 (세션 사이에는 매번 다시 조회).
- 사실 조회 경로도 버전 비교는 코드가 한다: LLM에게는 버전 목록 원본 대신 "그 Python에서 설치 가능한 최신 + 남은 취약점 수"를 넘긴다.

## 백엔드 API (FastAPI)
| 메서드·경로 | 하는 일 |
|---|---|
| POST /upload?session_id= | 요청 본문 = 파일 내용 그대로(1MB까지, python-multipart 없이) → 파싱 → 세션에 저장 → `{session_id, packages, excluded, saved}` |
| POST /chat | `{session_id?, message}` → ndjson 스트리밍: 첫 줄 `session`, 실행 이벤트들(이 세션 것만, 발생 순서), 마지막 줄 `final{intent, answer, plan, missing, conditions, confirmed, saved}`. "확정해줘"면 직전 제안 계획을 회차마다 저장해 `confirmed`에 ("1회차 확정해줘"처럼 회차를 말하면 그 회차만) (같은 계획 재확정은 중복 저장 안 함) |
| GET·POST /plans, GET·PUT·DELETE /plans/{id} | 계획 CRUD. 목록은 날짜순. 저장·수정·조회 응답에 `overlaps`(같은 날 시간이 겹치는 다른 계획). 수정은 날짜·시각·항목만 — v1.18: `status`(끝냄)·항목 `done_at`도. 목록은 `?session_id=`로 세션별 |
| GET /logs, GET·DELETE /logs/{session_id} | 실행 로그 목록·상세(순서대로)·삭제. 수정 주소 없음(405) |

- 오류 안내: 입력 오류는 422 `{"detail": "입력 형식을 확인해 주세요.", "fields": [...]}`, 없는 계획 404 "그런 계획이 없어요.", API 키 누락은 /chat final에 "서버 설정(API 키)을 확인해 주세요". 오류 상세는 로그 표에만.

## v1.18 고칠 것·더할 것 (2026-11-19 사용 중 발견)

### A. "처음부터" 뒤 다시 점검하면 끝나지 않는 것처럼 보임 (버그)
사용자 보고: 점검을 한 번 끝내고 "처음부터"를 누른 뒤 다시 점검하면 점검이 무한으로 도는 것 같고, 고쳐야 할 알약이 제대로 안 나온다.
2026-11-19 Claude Code 재현(헤드리스 Chrome, 실제 서버):
1. 업로드 → "우분투 22.04, Python 3.11, 2개, 11/25 매주" → 처방 완료
2. "처음부터"(세션 지움 + 새로고침) → 같은 파일 업로드 → "진료 시작"(= "패치 계획 짜줘")
3. 새 세션이라 조건이 비어 박사님이 OS·Python·N·날짜·간격을 되묻는다. 그런데 **상단 상태 칩이 "접수"(진행 중 단계)에 멈춘 채** 60초 넘게 그대로 → 진행 중으로 보인다. 알약은 계획이 없으니 블리스터로 가지 않는다.

고칠 것:
- **되묻고 끝난 턴의 상태 표시:** final에 `missing`이 있으면 상태 칩을 "정보 필요"(진행 표시 없음)로, 박사님은 끄덕이고 멈춘다. 어떤 턴이든 final을 받으면 진행 중 단계가 남지 않는다 (`clinicController.js` sendChatMessage 끝, `STEP_STAGE`).
- **"처음부터"가 무엇을 지우는지 말하기:** 지금은 파일·조건·대화가 모두 사라진다. 누르면 확인("파일과 조건을 모두 지우고 처음부터 할까요?")을 받고, 새로 시작한 뒤 박사님이 "새 차트입니다. 파일부터 올려 주시죠."라고 말한다.
- **업로드와 대화의 세션 엇갈림 (간헐):** 같은 날 한 번, 파일은 세션 A에 올라갔는데 바로 보낸 대화는 새 세션 B로 가서(B엔 패키지 0개) 박사님이 파일을 다시 달라고 했다(DB: A=패키지 3개·조건 없음, B=조건만). 다시 돌렸을 때는 재현 안 됨 → 업로드가 끝나기 전에 보낸 대화가 세션 없이 나간 것으로 의심. **업로드 중에는 보내기·진료 시작을 막고**("접수 중…"), 대화는 업로드가 준 세션으로만 보낸다. 테스트: 업로드 응답을 늦춘 상태에서 보내기를 눌러도 같은 세션으로 가는지.
- 확인: 위 1~3을 다시 해서 상태가 "정보 필요"로 바뀌고, 조건을 다시 말하면 계획이 나오고 알약이 블리스터로 가는지.

### B. 대화로 필요한 조건을 확실하게 받기
지금은 사용자가 어떤 값을 줘야 하는지, 박사님이 무엇을 알아들었는지 화면에 남지 않는다 (되묻기 말풍선을 닫으면 사라짐).
- **조건 칩 줄:** 입력창 바로 위에 `파일 · OS · Python · 한 번에 N개 · 첫 날짜 · 간격 · (시각)` 칩을 둔다. 받은 값은 값으로("Ubuntu 22.04", "Python 3.11", "5개", "11/25(화)", "매주", "22–24시"), 빠진 것은 "필요"로 강조. 값은 final의 `conditions`와 업로드 응답에서 채운다 (화면이 추측하지 않는다).
- 빠진 칩을 누르면 입력창에 예시 문장 조각을 넣는다 (예: OS → "Ubuntu 22.04"). 보내지는 않는다.

- 되묻기 문장은 지금처럼 빠진 것만. 칩 줄과 같은 이름을 쓴다.
- 모바일(375)에서는 칩 줄이 가로로 스크롤된다.

### J. 조건 칩: 입력창에 쓴 것도 보이게
사용자 보고: 입력창에 OS를 써 둬도 칩은 여전히 "OS 필요"라 뭔가 빠진 것처럼 보여 눌러야 할 것 같다. 보내면 서버가 알아듣는데, 보내기 전엔 그걸 알 수 없다.
- 칩 상태를 셋으로:
  | 상태 | 모양 | 뜻 |
  |---|---|---|
  | 받음 | 채운 청록 + 값 | 서버가 알아들은 조건 (final `conditions`·업로드) |

  | 필요 | 코랄 점선 + "필요" | 받지도, 입력창에도 없음 |

- "필요" 칩을 누르면 지금처럼 예시 조각을 넣는다. "입력창에 있음" 칩을 누르면 입력창에 초점만.

### M. 요일 규칙 (결정: 2026-11-19 사용자 "A 요일 규칙 추가")
- **조건에 `weekdays`(요일 목록, 0=월 … 6=일, 정렬·중복 없음)를 더한다.** 기존 `interval_days`는 그대로 둔다 (API 필드는 더하기만).
  - "매주 화·목" → weekdays [1, 3], "평일" → [0,1,2,3,4], "주말" → [5, 6], "매주 금요일" → [4] (weekdays [4] = 매주 금요일. interval_days 7과 같은 뜻이지만 요일이 명시됨).
  - **주 간격:** 요일과 함께 "격주"가 오면 2주마다 (`interval_days` 14 → 주 간격 2). 요일이 있을 때 interval_days는 7 또는 14만 의미가 있고(주 간격 1·2), 다른 값이면 요일을 따르고 interval_days는 무시한다(조건 한 줄에 요일만 보임 → 사용자가 바로 고침).
  - **"주 N회"처럼 횟수만 있고 요일이 없으면 요일을 지어내지 않는다.** `weekly_count`(N)만 받아 두고 박사님이 되묻는다: "주 2회라면 무슨 요일로 할까요? (예: 화·금)". 요일을 받으면 weekly_count와 요일 수가 달라도 요일을 따른다.
  - 요일 반복(weekdays) 또는 간격(interval_days) 중 하나만 있으면 "간격"은 채워진 것으로 본다 (`missing_inputs`의 interval_days 칸). 둘 다 새로 오면 이번 메시지의 것이 이긴다: 요일이 오면 interval_days를 지우고(7·14는 주 간격으로 바꿔 남김), N일 간격이 오면 weekdays를 지운다. 단, 요일이 이미 있는데 "매주로"·"격주로"(7·14)만 오면 요일은 두고 주 간격만 바꾼다 ("매주 화·목" → "격주로 바꿔줘" → 격주 화·목).
- **회차 날짜 (코드):** first_date부터 앞으로 가며 weekdays에 드는 날을 차례로 1·2·3회차에 쓴다 (first_date가 그 요일이 아니면 그 다음 맞는 요일부터). 주 간격 2면 첫 회차가 든 주 다음 주는 건너뛴다. MAX_ROUNDS(3)는 그대로.
- **캘린더 맞추기:** 요일 규칙이 있으면 겹칠 때 옮길 날도 **그 요일 중에서** 고른다 (`find_free_date`에 허용 요일을 넘김. SEARCH_DAYS 안에서 가장 가까운 맞는 요일). 맞는 빈 요일이 없으면 지금 규칙 그대로 원래 날짜를 두고 `calendar_conflicts`에 겹친 일정을 적는다. 옮긴 날이 다음 회차와 같은 날이 되면 다음 회차도 그 뒤의 맞는 요일로 민다.
- **표시 (코드가 만듦, LLM 아님):** 조건 한 줄·칩·처방 요약 모두 같은 함수 규칙.
  | 값 | 표시 |
  |---|---|
  | interval 1 / 2 / 7 / 14 / 21 / 30 / 90 | 매일 / 격일 / 매주 / 격주 / 3주마다 / 매월 / 분기마다 |
  | 그 밖 N | N일마다 |
  | weekdays [1,3] | 매주 화·목 |
  | weekdays [0..4] / [5,6] | 평일 / 주말 |
  | weekdays [1,4] + 주 간격 2 | 격주 화·금 |
  | weekly_count 2, 요일 없음 | 주 2회 (요일 필요) — 칩은 "필요" 상태 |
- **하지 않는 것:** "매달 첫째 주 화요일" 같은 몇째 주 규칙. LLM이 이걸 30일로 바꾸지 않게 프롬프트에 적고, 오면 박사님이 "몇째 주 규칙은 아직 못 합니다. 매주·격주·요일로 말씀해 주시죠."라고 말한다(`interval_unsupported` 표시로 코드가 문장을 고름).
- **DB:** sessions에 `weekdays`(TEXT, "1,3"), `weekly_count`(INTEGER) 열. 옛 DB는 지금처럼 자동 열 추가.
- **LLM 스키마(`Analysis`):** `weekdays: list[int] | None`, `weekly_count: int | None`, `interval_unsupported: bool`. 설명에 위 예를 넣고, "매달 n째 주"는 interval_days에 넣지 말라고 적는다.

  - 캘린더 일정에 `owner`(세션) 칸을 더하고 공개 모드에서는 그 세션 일정만 보고·넣고·지운다. 회차 겹침 판단·확정 등록도 그 세션 일정으로만.
  - 겹침 경고(`overlaps`)도 같은 세션 계획끼리만.
  - 화면의 "모든 계획 보기" 토글은 숨긴다 (`/health`가 `public: true`를 알려 줌).
- **호출 상한 (메모리, 서버 다시 켜면 초기화):** `/chat` IP당 시간당 20회·서버 전체 하루 300회, `/upload` IP당 시간당 60회. 넘으면 429 + "허허, 진료 대기가 길어졌네요. 잠시 뒤에 다시 오시죠." 값은 환경 변수로 바꿀 수 있음(`PUBLIC_CHAT_PER_HOUR`, `PUBLIC_CHAT_PER_DAY`, `PUBLIC_UPLOAD_PER_HOUR`).

- **공개용 DB:** `DB_PATH=data/public.db` (로컬 테스트 데이터와 분리).
- **실행:** `scripts/serve_public.sh` — 화면 빌드 → 공개 모드로 `127.0.0.1:8010`에 서버. Funnel 켜기/끄기는 사용자가 직접 (`tailscale funnel --bg 8010` / `tailscale funnel reset`). 안내는 `docs/deploy.md`.
- 업로드 1MB·메시지 2000자 제한은 지금 그대로.
- **DB (2026-11-19 추가):** WAL 모드(로깅 스레드가 쓰는 동안에도 읽기 가능), 색인 `plans(session_id, date)`·`calendar_events(owner, date)` (옛 DB는 칸을 더한 뒤 만듦). 공개 모드는 서버를 켤 때 `PUBLIC_RETENTION_DAYS`(기본 7)일 넘게 손대지 않은 세션과 그 계획·실행 로그·일정을 지운다 (로컬 DB는 안 지움). 구조(표 4개, 항목은 JSON 칸)는 그대로 — 그 안을 검색하는 기능이 없어 쪼갤 이득이 없음.

## 말투 (DR.PATCH)
- Agent는 **능청스러운 나이 든 박사님**처럼 말한다. 예: "허허, urllib3 1.24.1이라니… 꽤 오래 방치하셨군요."
- 능청은 **표현에만** 쓴다. 숫자·버전·날짜·심각도는 코드가 준 값 그대로, 없으면 "미상" / "확인 못 함".
- 실제 의료 조언처럼 읽히는 말("치료", "복용 권장" 등)은 쓰지 않는다. 서버 이야기임이 분명해야 한다.
- 답은 짧게: 회차별 핵심 한두 줄 + 필요한 경고. 꾸밈은 **굵게**와 "- " 목록만 (화면이 이 둘만 그린다).
- ~~고정 문구(되묻기·오류 안내)는 코드가 쓰므로 말투 규칙의 대상이 아니다.~~ (v1.17에서 바꿈 ↓)

### 말투 맞추기 (v1.17)
2026-11-19 사용자 확인: 지금 박사님 말이 처음 정한 말투(시제품 `prototype/drpatch-desk/index.html`의 대사)가 아니다.

- **고정 문구도 박사님 말투로 쓴다.** 코드가 쓰는 문장(접수·대기·되묻기·오류·진행 중 안내)은 지금 "계획을 세우려면 아래 내용이 더 필요해요", "requirements.txt 130개 패키지 접수됐습니다. 진료를 시작하거나 조건을 말씀해 주세요"처럼 평범한 안내문이다. 문장은 여전히 **코드가 만든다**(되묻는 항목은 빠진 것만, LLM에 맡기지 않음) — 말투만 바꾼다.
- **기준 대사 (시제품에서 정한 것):**
  - 맞이: "어서 오세요. 오늘은 어디가 불편한 서버인가요?"
  - 접수: "흠, 어디 보자… requirements.txt 130줄. 접수됐습니다."
  - 검사: "검사 들어갑니다. 따끔하지 않아요. 서버는요."
  - 발견: "허허, urllib3 1.24.1이라니… 꽤 오래 방치하셨군요."
  - 재계획: "Django 5.2는 Python 3.8로는 못 넘어가는군요. 처방 바꿉니다. Python부터 올리죠."
  - 회차: "급한 것부터 회차마다 5정씩 담습니다. 건강한 녀석들은 곡반으로."
  - 확정: "도장 찍습니다. 확정이에요." / "확정. 11/25 밤 10시에 뵙죠. 늦으시면 서운합니다."
  - 대기 중 누름: "검사 중엔 잠깐만요. 금방 끝납니다."
- **되묻기 예:** "흠, 차트를 채우려면 몇 가지가 더 필요합니다.\n- Python 버전 (예: 3.8)" / OS만 아는 경우 "맥이시군요. 버전만 알려 주시죠 (예: macOS 15)."
- **오류 안내 예:** "허허, 잠깐 기계가 말을 안 듣네요. 잠시 후 다시 해 보시죠." — 짧게, 원인 상세는 여전히 화면에 내지 않는다(NF3002).
- **LLM 답:** 2026-11-19 실제 답은 첫머리에 "허허," 한 번 붙이고 나머지는 보고서 문체였다. 프롬프트(`brain.py`)에 위 기준 대사를 예시로 넣고, 회차 줄마다 박사님 말로 짧게 쓰게 한다. 값(버전·날짜·등급)은 지금처럼 받은 그대로.
- 화면이 그리지 않는 꾸밈(백틱 \`코드\` 등)은 쓰지 않는다 — 2026-11-19 `chat` 답에 \`requirements.txt\`가 나옴.
- 확인: 고친 뒤 `scripts/run_agent.py`로 계획·되묻기·잡담 답을 하나씩 실제로 받아 기준 대사와 결이 같은지 본다.

## 테스트 방식
- 세 API의 실제 응답을 한 번 저장해 두고(tests/fixtures), 테스트는 저장본으로 돌린다. 네트워크 없이 `pytest` 한 번으로 판정.
- 꼭 있어야 할 테스트: 파싱(제외 줄 포함), 목표 버전 고르기, 호환 제약 위반 → Python 업그레이드 재계획, N 초과 회차 나누기, 겹침 경고, Tool 실패 시 나머지 진행, 로깅 꺼도 대화 정상.

## 완료 기준 (일상어)
- freeze 파일을 올리고 "5개까지"라고 하면 위험한 것부터 회차로 나뉜 계획이 나오고, 항목마다 "현재 → 목표 버전"과 이유가 보인다.
- 현재 Python에서 설치 안 되는 버전은 절대 목표 버전으로 나오지 않는다.
- 고칠 방법이 Python 업그레이드뿐이면, 업그레이드가 그 패키지보다 앞 회차에 들어간다.
- `-e`나 `>=` 줄은 조회 제외 목록에 보이고 오류가 나지 않는다.
- 파일 없이 "계획 짜줘"라고 하면 Tool을 부르지 않고 먼저 묻는다.
- 한 Tool이 실패해도 나머지 항목은 결과가 나오고, 실패한 항목엔 "확인 못 함"이 보인다.
- 같은 날 시간이 겹치는 계획을 저장하면 둘 다 저장되고 겹친다는 알림이 뜬다.
- 로그 탭에서 왜 이 순서·이 버전으로 정했는지, 왜 재계획했는지 볼 수 있다.
- 로깅이 멈춰도 대화는 정상 응답한다.
- 패키지 20개짜리 파일도 **60초 안에** 응답이 나오고, 기다리는 동안 실행 단계가 실시간으로 보인다 (실측 35.2초, docs/scenario-check.md)
