# 3. 설계 결정과 이유

각 결정: **무엇을 / 왜 / 버린 선택지 / 근거 문서**. 면접·발표에서 "왜 이렇게 했나요?"에 답하는 연습용.

## 도메인·기획
| 결정 | 왜 | 버린 것 | 근거 |
|---|---|---|---|
| 목표 버전 = "지금 Python에서 설치 가능한 최신 정식 버전" | 낮은 수정 버전은 뒤에 나온 취약점을 또 가짐. 최신 하나를 확인하면 패키지당 추가 호출 1번 | 가장 낮은 수정 버전부터 시도 | spec "목표 버전 고르기" 아래 "왜 바꿨나" |
| 대표 요청 "Ubuntu 언제까지?" → "지금 뭐부터?"로 교체 | LLM만으로도 지원 종료일은 대체로 맞힘 → Tool의 가치를 못 보여 줌 | 원래 요청 유지 | planning-check.md "도메인 조건 확인" |
| `packaging` 라이브러리 추가 | 버전 정렬·시험판 판별·requires_python 판정을 직접 짜면 틀리기 쉬움 | PEP 440 직접 구현 | decisions/2026-11-18-packaging.md |

## Tool
| 결정 | 왜 | 버린 것 | 근거 |
|---|---|---|---|
| 모든 Tool은 예외 대신 `{ok:false, error:{code}}` | Agent가 실패도 "값"으로 받아 판단·안내할 수 있음 | 예외 전파 | F3001, registry.py |
| 입력·출력을 pydantic 모델로 | LLM에 줄 입력 형식과 입력 검사가 한 곳에서 나와 어긋나지 않음 | dict 직접 작성 | spec v1.3 |
| 통신(http.py)과 해석(parse_*) 분리 | 해석은 저장본으로, 통신 실패는 가짜 transport로 네트워크 없이 테스트 | 테스트용 라이브러리(responses) | spec v1.4 |
| OSV 수정 버전은 ECOSYSTEM 범위만 | GIT 범위의 fixed는 커밋 해시 (테스트가 잡은 버그) | 전부 모으기 | test_vulns_grouped_by_aliases |

## Agent
| 결정 | 왜 | 버린 것 | 근거 |
|---|---|---|---|
| LLM은 Tool 종류·순서만, 반복 호출은 코드 | 패키지 20개를 LLM이 하나씩 부르면 느리고 빠뜨림 | LLM이 모든 호출을 직접 | AGENTS.md 규칙 |
| 되묻는 문장은 코드가 | LLM이 spec 밖 정보까지 물음 (실측) | LLM이 문장 작성 | spec v1.9 |
| LLM 부분을 `AgentBrain` 인터페이스 뒤로 | 가짜 LLM으로 그래프 전체를 네트워크 없이 테스트 | 실제 LLM으로만 확인 | brain.py, test_agent_graph.py |
| 재계획 1회 = Python 후보 줄기 하나를 get_eol로 확인 | "3번까지"를 셀 수 있게 정의가 필요했음 | 모든 Tool 호출을 세기 | spec "재계획" |
| 패키지마다 따로 최소 Python을 구함 | 한 패키지 조회 실패가 전체를 막던 문제 (리뷰 #2) | 모든 패키지를 한꺼번에 | review-day2.md |
| 사실 조회도 버전 비교는 코드가 | LLM에 버전 목록 원본을 주면 LLM이 계산하게 됨 (리뷰 #3) | 원본 전달 | fact_tools.py |

## 이벤트·로깅·저장
| 결정 | 왜 | 버린 것 | 근거 |
|---|---|---|---|
| 발행은 큐에 넣고 바로 돌아옴, 넘치면 버림 | 로깅 때문에 대화가 멈추면 안 됨 | 기다리기 | F3012~F3013, test_events.py |
| 로그 저장 순번은 DB 기준 | 서버 재시작하면 버스 순번이 1부터 → 로그 유실 (리뷰 #5) | 버스 순번 그대로 | repo.insert_event |
| 로그 수정 함수·주소 없음 | 로그는 사실 기록 (F3014) | — | test_no_update_function_for_logs |
| 직전 제안 계획을 세션에 저장 | "확정해줘"의 대상이 필요 | 확정 때 다시 계산 | spec v1.10 |

## API·화면
| 결정 | 왜 | 버린 것 | 근거 |
|---|---|---|---|
| /chat은 ndjson 스트리밍 | 20개 패키지면 30초 넘게 걸림 → 기다리는 동안 단계가 보여야 함 | 한 번에 응답, 폴링 | architecture.md 7절 |
| 업로드는 본문 그대로 | python-multipart 없이 가능 (라이브러리 추가 안 함) | 폼 업로드 | spec v1.12 |
| 화면도 FastAPI가 같은 주소로 | CORS 설정이 필요 없음 | 별도 서버(5500) | main.py |
| LLM 답은 escape 후 간단 서식만 | 스크립트 삽입 방지 | innerHTML 그대로 | render.js `esc`, `markdown` |

## 일하는 방식
| 결정 | 왜 |
|---|---|
| spec을 먼저 고치고 코드 | 명세와 코드가 어긋나지 않게 (spec 변경 기록 v1.0 → v1.13) |
| 완료 = 테스트 통과 + 실제 확인 스크립트 | 가짜 LLM 테스트가 못 잡는 문제가 있었음 (brain.py 중복 사고) |
| 다른 모델(agy)의 교차 리뷰 | 13건 지적 중 높음 3건을 찾음 |
